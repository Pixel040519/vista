# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

VISTA is a Student Monitoring System for elementary schools. It uses a monorepo structure with three services:

- **`vista-backend/node-api/`** — Express.js REST API (port 5000)
- **`vista-backend/fastapi-ai/`** — Python FastAPI AI microservice (port 8000)
- **`vista-dashboard/`** — React + Vite frontend (port 5173, proxies `/api` → port 5000)

## Development Commands

### Node.js API
```bash
cd vista-backend/node-api
npm install
npm run dev        # nodemon watch mode
npm start          # production
npm run migrate    # run DB migrations
```

### React Dashboard
```bash
cd vista-dashboard
npm install
npm run dev        # Vite dev server on :5173
npm run build      # production build
npm run preview    # preview production build
```

### FastAPI AI Service
```bash
cd vista-backend/fastapi-ai
pip install -r requirements.txt
PYTHONIOENCODING=utf-8 venv/Scripts/uvicorn main:app --reload --port 8000
```
> The venv must be created at `vista-backend/fastapi-ai/venv/` — if it was built at a different path, delete and recreate it with `python -m venv venv`. Always set `PYTHONIOENCODING=utf-8` on Windows to avoid emoji encoding errors in startup logs.

## Environment Setup

Copy `vista-backend/.env.example` to `vista-backend/node-api/.env`. Required vars:
- `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_PORT` — PostgreSQL connection
- `JWT_SECRET`, `JWT_REFRESH_SECRET`, `JWT_EXPIRES_IN` — JWT auth
- `PORT` — API port (default 5000)

The Vite dev server proxies `/api/*` to `http://localhost:5000`, so the frontend always calls relative `/api/` paths.

## Architecture

### Request Flow
```
React Dashboard → Node.js API (/api/*) → PostgreSQL
                                        → FastAPI (/api/ai/* proxied to :8000)
```

### Node.js API Route Structure (`vista-backend/node-api/src/`)
- `server.js` — Entry point, middleware setup, route registration
- `routes/` — One file per feature domain (auth, students, attendance, grades, behavior, dismissal, notifications, announcements, accounts, curriculum, score)
- `config/database.js` — PostgreSQL pool (max 20 connections), query wrapper, transaction helpers
- `config/migrate.js` — DB migration runner
- `middleware/auth.js` — JWT verification middleware

### FastAPI AI Service (`vista-backend/fastapi-ai/`)
- `main.py` — Entry point, router registration
- Routers: `/analyze` (VADER sentiment), `/predict` (grade prediction via Linear Regression), `/classify` (risk assessment including `/classify/risk/all` for all students — returns `attendance_factor`, `academic_factor`, `behavioral_factor`, and a derived `top_factor` per student), `/dashboard` (aggregated stats — attendance counts use distinct students, not raw records, with priority Present > Late > Excused > Absent when a student has multiple subject records), `/teacher-dashboard` (teacher-scoped dashboard summary in `routers/teacher_dashboard.py`; takes `teacher_id` + `sy_label` query params and returns assignments, today's attendance status per assignment, my-students rollup, risk distribution, students-to-watch, score-entry progress, recent behavior, ECE student count). The `score_entry_progress` array is **unrolled per (subject, section)** in Python. Since `score_items` are scoped per section, the SQL aggregates per `(subject_id, section)`; `components_total` is still subject-wide (pulled from `grading_structure`). `total_items` and `components_with_items` are **scoped to `latest_quarter`** (the highest-numbered quarter that has any items for that subject+section), so adding items in a new quarter resets those counters to reflect just that quarter's progress.
- Uses SQLAlchemy asyncpg dialect — **do not use Postgres `::type` cast syntax** (e.g., `:param::jsonb`, `:param::uuid`) in `text()` queries as it conflicts with SQLAlchemy's `:name` parameter binding. Use `CAST(:param AS type)` instead. Also avoid passing NULL parameters to `CAST()` — use conditional query building instead.


### React Dashboard (`vista-dashboard/src/`)
- `main.jsx` — Router setup, AuthContext provider
- `api/client.js` — Axios instance with JWT interceptors
- `pages/` — One component per route. `Dashboard.jsx` is a thin role router (~10 lines) that branches on `user.role` and renders `pages/dashboard/AdminDashboard.jsx` or `pages/dashboard/TeacherDashboard.jsx`. Admins keep the school-wide view; teachers get an action-oriented view scoped to their `activeAssignments`.
- `components/` — Shared UI components (`GradingConfigModal.jsx` for per-subject grading structure config, `AttendanceDetailModal.jsx` for drill-down attendance detail from dashboard stat cards)
- Routes: `/login`, `/` (dashboard), `/students`, `/students/:id`, `/attendance`, `/grades`, `/score-entry`, `/behavior`, `/securepass`, `/risk`, `/announcements`

## Database

PostgreSQL database `vista_db`. Schema is in `vista-backend/database/vistaDB_query.sql`.

Key tables and relationships:
- `users` — All accounts (admin, teacher, parent roles); uses `surname`/`first_name`/`middle_name` fields (no `home_address` column — removed)
- `students` — Student profiles with LRN, grade_level, section, QR code for SecurePass
- `parent_student` — Many-to-many guardian↔student relationships
- `class_assignments` / `teacher_assignments` — Teacher to class/subject mappings scoped to a school year; each (grade_level, section, subject, school_year) combination can only be assigned to one teacher (enforced by backend validation on create/update). Assignments are created under the active school year label (resolved via `getActiveSYLabel()`). When editing a teacher, only assignments for the active SY are deleted and replaced — historical assignments from prior years are preserved. Teacher assignments are copied when creating a new school year with "copy from".
- `attendance` — Per-subject daily records per student (Present/Absent/Late/Excused); has `subject_id` FK to `subjects`; unique on `(student_id, date, subject_id)` so each teacher records attendance independently per subject
- `subjects` — Curriculum subjects scoped to grade level and school year
- `grades` — Per-subject, per-quarter grades (auto-computed from score entry); `score` column = initial grade (weighted average), `grade` column = DepEd transmuted grade, `remarks` = "Passed"/"Failed"
- `grading_structure` — Configurable grading categories and components per subject (self-referencing via `category_id`); top-level rows (`category_id IS NULL`) are categories (e.g., Written Tasks 30%), child rows are components (e.g., Quizzes 15%)
- `score_items` — Individual assessments (e.g., Quiz 1, Long Test 2) under a grading component, scoped to **subject + section + quarter** so a teacher handling the same subject in multiple sections maintains independent items per section; has `highest_possible_score` (HPS) and `component_id` FK to `grading_structure`. Unique index: `(component_id, quarter, section, name) WHERE is_active=TRUE`.
- `student_scores` — Per-student raw scores for each score item; unique on `(score_item_id, student_id)`
- `behavior_logs` — Teacher observations with VADER sentiment compound score
- `risk_assessments` — AI risk classification (Stable/Moderate/High); factor columns (`attendance_factor`, `academic_factor`, `behavioral_factor`) are `DECIMAL(5,4)` (range 0–9.9999) — values must be normalized to 0–1 scale before insert (e.g., avg_grade 92 → 0.92)
- `academic_predictions` — Grade forecasts with confidence scores
- `dismissal_logs` — SecurePass QR scan/authorization records
- `school_years` — School year management; status is controlled by `is_active` (one at a time) and `is_upcoming` (one at a time); no `is_current` column
- `sections` — Class sections scoped to a grade level and school year
- `competency_domains` / `competency_skills` — ECE (Tots School) catalog; domains are top-level (e.g., "Phonemic Awareness"), skills belong to a domain. Soft-delete via `is_active=FALSE` once any record references them; hard-delete only when unused. Seeded in `2026_04_14_ece_competencies.sql` with 5 domains × 4 skills based on the NRYS manuscript.
- `ece_competency_records` — Per-student quarterly ECE ratings on the E/G/F/NA scale (Excellent/Good/Fair/Needs Assistance). Unique on `(student_id, skill_id, school_year_id, quarter)` so saving upserts rather than duplicates.

Supported grade levels: Pre-Nursery, Nursery, Pre-Kinder, Kinder, Grades 1–6.

## Key Conventions

- Authentication uses JWT (access + refresh tokens); the Node API validates tokens before all protected routes.
- The AI service is called by Node.js internally — the frontend never calls FastAPI directly. All AI endpoints are proxied through `ai.routes.js`: `POST /api/ai/predict-performance`, `POST /api/ai/risk-assessment`, `GET /api/ai/risk-all`, `POST /api/ai/sentiment`, `GET /api/ai/dashboard-summary`, `GET /api/ai/teacher-dashboard`, `GET /api/ai/class-health` (single student, teacher-only), `GET /api/ai/class-health/all` (bulk, teacher-only). The frontend uses `aiApi` methods from `api/client.js` (`aiApi.teacherDashboard()`, `aiApi.classHealth(id)`, `aiApi.classHealthAll()`).
- `GET /api/ai/risk-all` is open to admin + teacher, but teachers receive a payload **scoped server-side** to their `(grade_level, section)` set: the Node proxy looks up the teacher's `teacher_assignments` rows for the active SY, filters the FastAPI result, and recomputes `summary` counts. FastAPI itself stays role-agnostic — access control lives in the Node proxy where the JWT is validated. **Note:** The Risk Overview frontend page (`pages.jsx` `RiskOverview`) only uses `/risk-all` for admins; teachers call `/class-health/all` instead so the numbers reflect their own subjects/attendance/behavior logs rather than school-wide data. `/risk-all` is still reachable for teachers (legacy) but no UI currently consumes it.
- **Class-health** (`/api/ai/class-health` + `/api/ai/class-health/all` in `ai.routes.js`): teacher-scoped rule-based signals computed entirely in Node. Three metrics — Academic (latest-quarter grade per subject, averaged; <75 urgent, 75–79.9 watch, ≥80 ok; `insufficient` when no rows), Attendance (last 30 days in teacher's subjects; <0.70 urgent, 0.70–0.849 watch, ≥0.85 ok; `insufficient` when total <5), Behavior (teacher's own `behavior_logs` this month; avg_sentiment <-0.30 urgent, -0.30–-0.001 watch, ≥0 ok; `insufficient` when log_count <2). Overall band = worst of non-insufficient metrics. Shared band helpers `bandAcademic/bandAttendance/bandBehavior/overallBand` live at file scope in `ai.routes.js` so both endpoints (and by extension the Student Detail "In Your Class" card, the teacher Risk Overview page, and the TeacherDashboard widgets) stay in sync. The single-student endpoint also returns a DSS `suggestions[]` array with deep-link actions (`score-entry` / `attendance` / `behavior`); the bulk endpoint does not — it returns per-student `overall_band`, `top_concern` (tie-break: academic > attendance > behavior), and three `metrics.{academic,attendance,behavior}` objects, sorted urgent → watch → ok → insufficient with worst metric value breaking ties within a band. Bulk query strategy: one roster query + three per-section-group metric queries (separate per `(grade_level, section)` so a teacher teaching Math in Grade 4-A and Science in Grade 5-B never cross-counts). Students are loaded with `WHERE is_active = TRUE` (the `students` table has no `status` column).
- `GET /api/ai/teacher-dashboard` resolves the teacher from the JWT (`req.user.id`) and the active SY label, then forwards both as query params to FastAPI's `/teacher-dashboard/summary`. The frontend never sends teacher_id directly.
- Behavior logs store a `vader_compound` score (−1 to 1) alongside the teacher's raw observation text. **Writes are teacher-only**: `POST/PUT/DELETE /api/behavior[/:id]` use `authorize('teacher')`, and PUT/DELETE WHERE clauses include `teacher_id = req.user.id` so a teacher can only edit/delete their own logs. POST validates that the target `student_id` is in one of the teacher's active-SY `teacher_assignments` sections (via the file-scope `teacherOwnsStudent` helper in `crud.routes.js`) and 403s otherwise. `GET /api/behavior` branches by role: teachers still pass `student_id` and see only their own logs (but if the student is not in their classes, the endpoint returns `{logs:[], total:0}` so `StudentDetail` doesn't break); admins may omit `student_id` and pass any combination of `student_id`, `teacher_id`, `grade_level`, `section`, `category`, `sentiment`, `date_from`, `date_to`, `limit`, `offset` — response is `{logs, total}` with `logs` joined to `students` (`first_name`, `middle_name`, `surname`, `grade_level`, `section`) plus a correlated `subject` field derived from `STRING_AGG(DISTINCT ta.subject)` on `teacher_assignments` joined via `(teacher_id, s.grade_level, s.section)` (so the admin detail modal can show what subject the teacher was assigned for that class). Both the list and count queries JOIN `students s` so `s.grade_level` / `s.section` filters resolve. `GET /api/behavior/summary` (admin-only) takes the same filter set (including class scoping) and returns `{total, positive, neutral, negative, this_week}`. Frontend: `pages.jsx` `Behavior()` is a thin role router over `TeacherBehavior` and `AdminBehavior`. **TeacherBehavior** shows a Class dropdown scoped to `activeAssignments`, then a Student search input (admin-style autocomplete searching by name or LRN via `studentApi.list({grade_level, section, search})`), plus the existing log cards + modal. Log card avatars show a teal Pencil icon + "Logged by you" instead of the teacher's name (teachers only ever see their own logs). **AdminBehavior** is a read-only school-wide browser: 4-card stat strip (Total/Positive/Neutral/Negative via `behaviorApi.summary`), filter card laid out as 4 columns on `lg:` — Student (search by name/LRN with autocomplete dropdown), Class (grade_level + section combined from `curriculumApi.getSections()`), Category, Sentiment. Picking a student auto-fills the Class filter from the student's `grade_level`/`section` and **disables** the Class dropdown; typing in the Student search or clicking the Clear button at the top of the filter card unlocks Class by clearing `student_id`+`grade_level`+`section` together. Table columns are Student (linked to `/students/:id`) · Class · Category · Sentiment · Teacher · Details — the Details button opens a Modal with Student/Teacher/Date & Time/Subject/Category/Sentiment (with sentiment_score) and the full observation text; **no** Log/Edit/Delete actions. Paginated 50/page.
- SecurePass uses QR codes generated per-student; dismissal requires matching an authorized guardian. The scanner lives at `/securepass/scan` (`pages/SecurePassScan.jsx`) and uses `html5-qrcode` to open the device camera, auto-submitting decoded payloads to `POST /api/dismissal/verify`. Camera access requires HTTPS in production (localhost is fine for dev). The `/securepass` page (`pages.jsx` `SecurePass`) is oversight-only: stat strip (dismissed / failed / total today), "Open Scanner" CTA, today's dismissal log table, and a collapsible manual-entry fallback (paste JSON) for when the camera fails.
- **ECE Competency Module** (manuscript pillar 2b + 3c): teacher-facing quarterly tracker for Pre-Nursery to Kinder. Backend lives in `ece.routes.js` mounted at `/api/ece` — `GET/POST/PUT/DELETE /domains` and `/skills` (admin-only), `GET /records?grade_level=&section=&quarter=` (returns roster + existing ratings for a class+quarter), `POST /records` (bulk upsert with `ON CONFLICT` on the unique index). Teacher access is enforced by `verifyEceAssignment()` which checks `teacher_assignments` for the active SY and rejects non-ECE grade levels. Frontend: `pages/EceCompetency.jsx` at `/ece-competency` (teacher-only route), reachable via the "Today's Work" sidebar group (Baby icon). The page auto-filters class options to ECE grades from `activeAssignments` and renders one table per domain with an E/G/F/NA button grid per (student × skill); clicking a rating twice clears it. Save is a single bulk POST. Admin catalog CRUD lives as a new "ECE Catalog" tab in `CurriculumManagement.jsx` (`EceCatalogPanel` component) — inline add/edit/delete for domains and skills; domains/skills with existing records are soft-deleted (archived) instead of hard-deleted. The `eceApi` client methods in `api/client.js` cover both teacher and admin flows.
- All name fields use `surname`, `first_name`, `middle_name` (not a single `full_name` field).
- School year status: exactly one may be `is_active` (enforced in a transaction); multiple may be `is_upcoming`; all others are archived. The backend enforces both constraints in transactions. Past years (end year ≤ current year) cannot be set to upcoming. The `resolveSYId` helper falls back to the active school year when no `sy_id` is provided.
- Account Management: the teacher list and assignment-related queries (`GET /api/accounts/teachers`, `GET /api/accounts/assignments`, `getAssignments()` helper) are scoped to the active school year. Each teacher row has a History button (clock icon) that opens a modal showing all assignments grouped by school year (via `GET /api/accounts/teachers/:id/assignment-history`). When editing a teacher, the Teaching Assignments section has a "Copy from..." dropdown that lists previous school years (excluding the active SY) with assignment counts; selecting a year replaces the current assignment rows with that year's assignments.
- Grading structure percentage fields reject negative values (clamped to 0). Category weight fields turn red when the total exceeds 100%; component weight fields turn red when their total exceeds the parent category's weight. The grading config modal has a "Copy from" button that lets you copy another subject's grading structure (filtered by grade level).
- Grading structure: each subject can have a configurable grading breakdown (categories + components with percentage weights). The `grading_structure` table uses `category_id` (self-referencing FK) where `NULL` = top-level category, non-NULL = component under that category. Category weights must sum to 100%; component weights must sum to their parent category's weight. Grading structures are copied when creating a new school year with "copy from". The curriculum management UI exposes a per-subject grading config modal (sliders icon). Editing grading structure preserves existing UUIDs (update in place, not delete-and-recreate) so `score_items.component_id` FK references remain valid. Categories/components with recorded student scores cannot be deleted — the backend blocks it and the frontend grays out delete buttons.
- Score entry: teachers can only access their own teaching assignments. The filter bar shows a "Class" dropdown (grade_level + section pairs derived from the teacher's active SY assignments) and a "Subject" dropdown filtered to subjects the teacher is assigned to for that class. The backend enforces assignment ownership via `verifyTeacherAssignment()` on all score endpoints (GET/POST scores, GET breakdown, GET/POST score items). **Score items are scoped per section**: `score_items` has a `section` column, and the unique index + all queries (`GET/POST /api/scores/items`, `GET/POST /api/scores`, `GET /api/scores/breakdown`) filter by `section`. A teacher handling the same subject in two sections therefore maintains completely independent score items per section — adding/removing an item in one section does not affect the other. The frontend passes `grade_level` + `section` in `scoreApi.getItems` and `scoreApi.saveItems`. Teachers create score items (e.g., Quiz 1, Quiz 2) under grading components via a modal, then enter raw student scores in a spreadsheet-like grid. The system auto-computes T (total) → PS (percentage score = T/HPS×100) → WS (weighted score = PS×weight/100) per component, rolls up to category totals, and saves the final quarterly grade to the `grades` table. Score items with recorded scores cannot be deleted; items without scores are hard-deleted from DB. Adding a score item requires both a name and a valid HPS (> 0) — the frontend validates before saving. **The "save items" action also accepts an empty list**, so removing the only remaining item in a component and saving is allowed (the backend deletes items not in the payload). Filter selections (class, subject, quarter) and expanded component state persist in `sessionStorage` under the key `vista_score_entry_filters` (managed by `usePersistedFilter`) across navigation and refresh. The school year filter is locked to the active school year (displayed as read-only "SY 2025-2026"). A migration to add the `section` column and backfill from `student_scores → students.section` (with `teacher_assignments` fallback) lives at `vista-backend/database/migrations/2026_04_11_score_items_section.sql`.
- DepEd transmutation (DO 8, s. 2015): initial grades (weighted averages) are transmuted to a 60–100 scale before saving as the final grade. The `transmuteGrade()` function exists in both backend (`score.routes.js`) and frontend (`ScoreEntry.jsx`). Formula: initial ≥ 100 → 100; initial ≥ 60 → 75 + floor((initial−60)/1.6) capped at 99; initial > 0 → 60 + floor(initial/4) capped at 74; else 60. Passing = transmuted ≥ 75.
- Excel export: the Score Entry page has an "Export Excel" button (uses `xlsx-js-style`, dynamically imported to avoid Node polyfill warnings) that generates a DepEd-format grading sheet with colored category/component headers, HPS row, students grouped by gender (Male/Female), and T/PS/WS/IN/F/Remark columns. T, PS, WS, IN, F, and Remark cells use Excel formulas so the spreadsheet auto-recalculates when scores are edited. PS, WS, and IN values are rounded to 2 decimal places via `ROUND()` formulas. Export is blocked if any component has no score items. The Vite config aliases `xlsx-js-style` to its browser bundle (`dist/xlsx.bundle.js`) to avoid Node `stream`/`events`/`buffer` externalization warnings.

## Role-Based Access

- **Admin**: Full access to all pages except Attendance and Score Entry (teacher-only). Can manage accounts, curriculum, students, and view student details. Risk Overview shows all students school-wide using the school-wide `risk_assessments` table via `/api/ai/risk-all`.
- **Teacher**: The `/api/auth/me` and `/api/auth/login` endpoints return `assignments` (grade_level, section, subject, school_year) and `active_school_year` (label of the active SY) for teachers. The `AuthContext` exposes `activeAssignments` — assignments filtered to the active school year. Teacher-facing pages (Students, Attendance, Score Entry) use `activeAssignments` to show a "Class" dropdown filtered to their assigned sections instead of open grade/section filters. Attendance and Score Entry are teacher-only in both sidebar and route guards. Attendance backend: GET is open to admin+teacher (student detail page uses it), POST is teacher-only and requires `subject_id`. **Risk Overview** is open to teachers (route `roles={['admin','teacher']}`) — for teachers, `RiskOverview` branches into a separate `TeacherRiskOverview` sub-component that calls `aiApi.classHealthAll()` and renders a class-health-banded table (Urgent / Watch / On track / Not enough data) with per-row overall band pill, top-concern column, and three numeric mini-chips (Academic `avg_grade.toFixed(1)`, Attendance `%`, Behavior signed `avg_sentiment.toFixed(2)`) each tinted by their per-metric band. This is the teacher-accurate replacement for the legacy school-wide High/Moderate/Stable pills, which had misled teachers by mixing in signals from other teachers' subjects/sessions/logs. Admin rendering of Risk Overview is unchanged. The teacher dashboard (`pages/dashboard/TeacherDashboard.jsx`) is action-oriented: greeting, today's pending attendance per `(class, subject)`, my-students stat cards, my-classes grid, score-entry progress, recent behavior logs, and an ECE competency placeholder card (only rendered when any of the teacher's `activeAssignments.grade_level` is in {Pre-Nursery, Nursery, Pre-Kinder, Kinder}). The Score Entry Progress widget shows **one row per (subject, section)** — a teacher with the same subject in two sections sees two rows, each with its own Resume button that deep-links to the correct class via `goToScoreEntry(sp.grade_level, sp.section, sp.subject_id, sp.latest_quarter)`. The handler writes `selectedClass`, `subjectId`, and `quarter` into the `vista_score_entry_filters` sessionStorage blob (the same key `ScoreEntry.jsx` reads via `usePersistedFilter`) so the Score Entry page mounts with the clicked row's class, subject, AND quarter preselected (falling back to Q1 if `latest_quarter` is null). React keys use `${subject_id}-${section}` to stay stable across multi-section duplicates. The widget refetches on `window` focus so adding a score item in another tab updates the count when the user tabs back. The **Today's Action Items** widget's "Take attendance" / "Review" buttons use `goToAttendance(gradeLevel, section, subjectId)` which passes the deep-link through **React Router location state** (`navigate('/attendance', { state: { deepLink: { selectedSection, selectedSubject, ts: Date.now() } } })`), not sessionStorage. The Attendance page reads `location.state.deepLink` in a `useEffect([location.state])` and re-applies the selection whenever a fresh `ts` arrives — this is required because React Router may keep the Attendance component mounted across repeated dashboard→attendance trips, so a mount-only read would miss the second click. `appliedDeepLinkTs` ensures each timestamp is only applied once; the target subject is stashed in a `useRef` and consumed by the subject-load effect once the subject list arrives for the new section. **TeacherDashboard data sources**: the page fetches `aiApi.teacherDashboard()` AND `aiApi.classHealthAll()` in parallel via `Promise.allSettled`. The **Needs Attention** stat card (was "At-Risk Students"), **My Classes** section grid, and **Students to Watch** list all derive from the class-health payload — band counts come from `chSummary.urgent/watch/ok/insufficient`, `mySectionsHealth` groups `classHealth.students` by `(grade_level, section)` and merges with `classHealth.scope.sections` for subject lists, and `studentsToWatch` filters to urgent+watch and caps at 5 (clickable rows link to Student Detail). Everything else on the dashboard (attendance rollup, today's action items, score-entry progress, recent behavior, sentiment mini, ECE card) still comes from the FastAPI `/teacher-dashboard/summary` proxy. This split keeps class-health as the single source of truth for teacher-scoped band numbers across Student Detail → Risk Overview → TeacherDashboard — the same numbers appear in all three views because they share the same endpoint + band helpers.
- **Parent**: Limited access; students endpoint filters to linked students via `parent_student` table.
- Student Detail page (`pages/StudentDetail.jsx`) is teacher-aware: teachers do not see the **Generate QR** button, the **Home Address** card, or per-guardian email/phone/home_address rows (guardian names, relationship, and emergency/pickup chips remain so teachers still know who is authorized to fetch a student). Backend defense-in-depth: `GET /api/students/:id` strips `home_address` and per-guardian `email`/`phone`/`home_address` when `req.user.role === 'teacher'`, and `POST /api/students/:id/generate-qr` is now `authorize('admin')` only — SecurePass token generation from a profile is admin-only per the manuscript's "Administrator / Security Oversight" scoping. The Attendance tab table shows Date / Status / **Subject** / Recorded By columns — the Subject column renders `subject_name` from the `GET /api/attendance` join (`crud.routes.js` joins `subjects` on `a.subject_id`) so teachers can see which subject each record belongs to, since attendance is scoped per subject.
- Teacher assignments are unique per (grade_level, section, subject, school_year) — the backend rejects duplicates on create/update scoped to the active school year, and the frontend disables already-taken subjects in the assignment dropdown (showing the assigned teacher's name). In the subject dropdown, available subjects use normal color; taken subjects are red with inline `style` to override the parent `<select>` color.

## Frontend UI Patterns

### Branding
- The school logo (`NRYS_logo.png`) is stored at `vista-dashboard/src/assets/NRYS_logo.png` and imported as `nrysLogo`. It appears in three places: Sidebar header, Login page desktop (left panel), and Login page mobile. The Login page features a centered school seal with "Northern Rizal Yorklin School" heading and "VISTA Student Monitor" subtitle with teal accent lines, a feature grid (AI Predictions, Risk Detection, SecurePass QR, Parent Connect), and the school motto "Knowledge · Benevolence · Courage". The sidebar logo uses explicit `width`/`height` attributes and inline `objectFit`/`display` styles for cross-browser compatibility (Chrome rendering fix).

### Sidebar Navigation
- `Sidebar.jsx` defines two parallel `navGroups` arrays — `adminNavGroups` and `teacherNavGroups` — and selects which one to render via `user?.role === 'teacher' ? teacherNavGroups : adminNavGroups`. The per-item `roles` filter still runs on top, so cross-role items (e.g., SecurePass QR) keep working in either array.
- **Admin sidebar** has 4 groups: **Overview** (Dashboard), **Student Management** (Students, Attendance [teacher-only, hidden for admin], Grades, Score Entry [teacher-only, hidden for admin], Behavior), **Tools** (SecurePass, Risk Overview, Announcements), **Administration** (Accounts, Curriculum).
- **Teacher sidebar** is reorganized around the daily teaching workflow: **Overview** (Dashboard), **Today's Work** (Attendance, Score Entry, ECE Competency — promoted to the top group so daily action surfaces are one click away), **My Students** (Students, Behavior, Risk Overview), **Communication** (Announcements). Grades is admin-only and not shown in the teacher sidebar (teachers view/enter grades via Score Entry). ECE Competency is teacher-only and the page itself renders an empty state if the teacher has no Pre-Nursery/Nursery/Pre-Kinder/Kinder assignments, so the sidebar entry is safe to show for all teachers. There is no "Administration" group for teachers.
- Groups with no visible items for the user's role are auto-hidden by the existing `visibleItems.length === 0` guard.
- The Grade Summary table in Score Entry groups students by gender (Male/Female) with separator rows, shows category weighted scores, initial grade, transmuted final grade (color-coded: teal ≥ 75, red < 75), and a Passed/Failed remarks pill. Category header columns use `truncate` with `max-w-[160px]` to handle long names.

### Responsive Layout
- The sidebar (`Sidebar.jsx`) is hidden on mobile (`-translate-x-full`) and slides in via a hamburger menu in the Topbar; it is always visible on `lg:` (1024px+) screens.
- `Layout.jsx` applies `lg:ml-64` so main content is full-width on mobile and offset on desktop. The main content wrapper uses `min-w-0` to prevent flex children with long text from overflowing the viewport. The sidebar open/close state is managed in Layout and passed as props (`open`, `onClose`) to Sidebar.
- The Topbar shows a `Menu` hamburger icon on mobile (`lg:hidden`) and triggers `onMenuToggle` to open the sidebar.

### Modal (Portal)
- The shared `Modal` component (`components/UI/index.jsx`) renders via `createPortal` into `document.body` so it always sits above the sidebar and layout regardless of stacking context.
- On mobile, modals slide up from the bottom (`items-end`, `rounded-b-none`); on `sm:` and above, they center on screen.

### Tables
- All `table-base` tables must be wrapped in a `<div className="overflow-x-auto">` container to enable horizontal scrolling on narrow screens.
- Table header cells use `whitespace-nowrap` to prevent awkward column header wrapping.

### Responsive Breakpoints
- Use mobile-first Tailwind: base styles for mobile, then `sm:` (640px), `md:` (768px), `lg:` (1024px) for larger screens.
- Page titles: `text-xl sm:text-2xl`. Page subtitles: `text-xs sm:text-sm`.
- Page headers should use `flex-wrap gap-3` so action buttons wrap below the title on small screens.
- Form grids inside modals: prefer `grid-cols-1 sm:grid-cols-2` over a hard `grid-cols-2`.
- The `BrowserRouter` in both `App.jsx` and `main.jsx` has `v7_startTransition` and `v7_relativeSplatPath` future flags enabled.
- The body has `select-none` and `cursor-default` globally; `user-select: text` and `cursor: text` are re-enabled on text-type `input` and `textarea` elements; `checkbox` and `radio` inputs use `cursor: pointer`; `select` elements use `cursor: pointer`. This prevents the text caret from appearing on non-interactive elements like titles, headers, and hints.
- All input fields use `onKeyDown` to blur on Enter key press for consistent UX across the app.
- Drag-and-drop reordering (via HTML5 DnD API + grip handle) is used in the grading config modal for categories and in the score items modal for items.
- Attendance page: teacher sees a "Class" dropdown (assigned sections), a "Subject" dropdown (filtered to the teacher's assignments for that class, auto-selected if only one), and a date picker. Attendance is scoped per subject — each teacher records attendance independently for their assigned subject. The subject dropdown resolves subject names to UUIDs via `curriculumApi.getSubjects`. Changing the date or subject loads existing attendance records via `GET /api/attendance/bulk` (with `subject_id` filter) and auto-selects the saved statuses. Clicking an already-selected status deselects it. The `POST /api/attendance` endpoint requires `subject_id` in each record and upserts on `(student_id, date, subject_id)` so re-saving updates existing records without overwriting other teachers' records.
- Dashboard attendance stats: the "Present Today" stat card counts students whose best status is Present or Late (i.e., attended at least one subject). The "Absent Today" card counts students absent in all logged subjects. Both cards are clickable — they open `AttendanceDetailModal` with Present/Absent tabs. The modal fetches `GET /api/attendance/daily-detail?date=` (returns per-student, per-subject rows) and groups students by Grade Level → Section (both collapsible, sections collapsed by default). Each student row shows per-subject status badges (P/L/E/A). Students present in some subjects but absent in others are flagged with a "Possible skipping class" amber badge. The `StatCard` component accepts an optional `onClick` prop for clickable cards.
- Students page: teachers see a "Class" dropdown and search with labels; Grade Level and Section columns are hidden (redundant). Admin sees full grade/section filter dropdowns.
- Risk Overview page: filter tabs (All / High Risk / Moderate Risk / Stable) wired to a `filter` state, sorted by `risk_score` descending. Columns are Student (clickable link to `/students/:id`), Grade & Section, Risk Level pill (color-coded), Risk Score (progress bar), Top Factor (Attendance / Academic / Behavioral — derived server-side from the max of the three factor columns), and Last Assessed. Title/subtitle adapt for teachers ("...students in your assigned classes"). Empty state distinguishes "no data at all" (with teacher-specific copy) from "no matches for current filter".
