# VISTA Mobile — CLAUDE.md

Flutter monorepo for the two mobile deliverables from the VISTA manuscript (Chapter 1, Apr 2026):

- `vista_parent/` — Parent app. Login, per-child Overview (risk + signals) / Attendance / Academics / Behavior / Pickup QR / Dismissal History, plus Profile (read-only summary + Edit Profile screen with name/phone update, profile-photo upload, password change) and an Authorized Fetchers manager (add/edit/delete non-account pickup persons with photos). FCM push for pickup events. Conditional-access 423 Locked screen when a child's academic view is suspended by admin.
- `vista_guard/` — Security guard app. QR scanner that hits `/api/dismissal/verify`, today's log, offline retry queue, idle PIN re-lock.
- `packages/vista_api/` — Shared Dart package. `ApiClient` (Dio + JWT interceptors + single-flight refresh), `AuthRepository` (secure-storage token cache), DTOs, `ParentApi` / `GuardApi` method wrappers. Both apps depend on this package via a relative path.

## Backend contract

All mobile traffic goes to the Node API at `:5000` — never FastAPI directly (auth + role checks live in Node).

Parent-relevant endpoints introduced in Phase 1 of the mobile plan (`2026_04_22_*` migrations):

- `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /api/auth/me` — reused from the web dashboard.
- `GET /api/students`, `GET /api/students/:id` — filtered server-side to linked students for `role=parent`.
- `GET /api/attendance?student_id=` — `enforceParentLinked` on the Node side.
- `GET /api/grades?student_id=` — `enforceParentLinked`; returns `423 Locked` with `{reason}` when `students.academic_access_suspended`.
- `GET /api/ece/student-records?student_id=&quarter=&sy_id=` — same guards; returns `{ school_year, student, skills[], records[] }` for the ECE Academics tab.
- `GET /api/behavior?student_id=` — `enforceParentLinked`.
- `GET /api/dismissal/logs` — parent branch returns last 30 rows across every linked student.
- `POST /api/students/:id/generate-qr` — parent branch: only `is_authorized_pickup = TRUE` guardians. Optional body `fetcher_type` (`'self'` default | `'auth'`) + `fetcher_id` binds the QR to a chosen fetcher. `'auth'` requires a UUID from `/api/pickup-persons` owned by the caller for this student. Server stores the binding on `students.qr_fetcher_type` / `qr_fetcher_id`. **Expiry policy branches on fetcher type**: `'self'` keeps the 20-minute timer (parent has account access to refresh), `'auth'` is one-time use only with no timer (the authorized fetcher cannot refresh from outside the parent's app). The response includes `expiresAt` for `'self'` and `null` for `'auth'`.
- `GET/POST/PUT/DELETE /api/pickup-persons` — parent-only CRUD for non-account fetchers (yaya, lola, driver, etc.) scoped to `(parent, student)`. POST + PUT are multipart with a required `photo` field on POST. The Pickup QR tab's "Manage authorized fetchers" screen wraps these.
- `POST /api/profile/me/photo` — multipart photo upload for the parent's own avatar (field `photo`). Response mirrors `PUT /me`. After upload the Edit Profile screen calls `ref.invalidate(sessionProvider)` so the new `photo_url` flows back through `/me` into the chip selector and dismissal screens.
- `GET /api/ai/parent-summary/:student_id` — lightweight Overview rollup (risk, 30d attendance, latest quarter academic or ECE dist, last behavior log, unread notification count). The `risk` block includes a `factors` object (`{attendance, academic, behavioral, competency}`) read straight from the `risk_assessments` row; the parent-app Overview risk card uses these to render a "What's driving this" section under the chip with up to two plain-language drivers, each tappable to deep-link into the relevant tab. The `attendance` block is **day-based via per-day BOOL_OR collapse** — total_days = distinct calendar dates with any attendance row in the last 30 days; present_days = dates where any subject was Present/Late. Per-subject session counts are intentionally NOT used here — the card label reads "X of Y days present" so the units must match. The Attendance tab below counts rows per-subject, so its numbers can legitimately differ.
- `GET /api/notifications`, `PATCH /api/notifications/:id/read` — in-app bell (server-side notification rows are written on every dismissal verify, so the history survives an FCM drop).
- `POST /api/devices/register`, `DELETE /api/devices/:token` — FCM token registry. The vista_parent app calls register after login + permission grant, and delete on logout.
- `PUT /api/profile/me`, `PATCH /api/profile/me/password` — self-service profile edit (name parts + phone) and password change. Role-agnostic (shared with the web dashboard); the parent app's Edit Profile screen wraps both. After a successful PUT the screen calls `ref.invalidate(sessionProvider)` so `/me` is re-fetched and the Profile screen reflects the new name. Password change does NOT rotate JWTs — existing tokens stay valid.

Guard-relevant endpoints:

- `POST /api/auth/login` — reject non-guard role inside the app UI with a role-mismatch error.
- `POST /api/dismissal/scan` — Step 1 of the two-step verify flow. Body `{ qrPayload }`. Decodes the QR, returns `{ student, authorizedGuardians[], expiresAt }` (where `expiresAt` is `null` for 'auth'-bound QRs) without consuming the QR. Each guardian object carries `photo_url: string|null` and `kind: 'self' | 'auth'`. Branches on `students.qr_fetcher_type`: `'self'` returns the single bound parent (with profile photo), `'auth'` returns the single `authorized_pickup_persons` row (with its photo), NULL falls back to the full authorized-parent list (legacy / admin-generated QRs) — the guard app then shows the picker.
- `POST /api/dismissal/verify` — Step 2. Body `{ qrPayload, authorized_by_id, fetcher_type, gate_label? }`. `authorized_by_id` is the UUID from the matching guardian object; `fetcher_type` is the `kind` field forwarded verbatim so the server validates against the right table (`parent_student` vs `authorized_pickup_persons`). For `'auth'` rows the server resolves the responsible parent and stamps `dismissal_logs.authorized_by = parent_id` + `fetcher_authorized_id = <auth row>` so the existing parent-notifications JOIN keeps working. `gate_label` is the guard's entrance setting persisted on the log row.
- `GET /api/dismissal/logs?date=today` — powers the "Today's log" tab; the rows now include `gate_label` when present.
- `POST /api/students/:id/generate-qr` — also stamps `students.qr_generated_by = req.user.id` so the guard-side `/scan` can identify the parent who pressed Generate.

## Role rules

- `security_guard` is a distinct role (migration `2026_04_22_add_security_guard_role.sql`). Only super_admin may create one (Accounts → Guards tab — see Phase 6).
- `parent` role was already present but previously had no UI. The mobile app is its entry point.

## QR format (DO NOT CHANGE)

SecurePass QR payload across web + both mobile apps. The `expiresAt` field is **conditional** — present for parent-self / admin QRs, absent for 'auth'-bound QRs (authorized pickup person):

```json
// self / admin
{ "studentId": "<uuid>", "token": "<uuid>", "expiresAt": "<iso>", "type": "VISTA_SECUREPASS" }
// auth (no timer — single use only)
{ "studentId": "<uuid>", "token": "<uuid>", "type": "VISTA_SECUREPASS" }
```

`vista_parent` renders this with `qr_flutter`; `vista_guard` decodes with `mobile_scanner` and POSTs verbatim to `/api/dismissal/scan` then `/api/dismissal/verify`. Both endpoints parse `expiresAt` conditionally (skip the time check when absent). One-time-use invalidation by a successful `/verify` (server clears `students.qr_code`) applies to every variant.

## Conditional access

When academic view is suspended, the backend returns:

```
HTTP 423 Locked
{ "error": "Academic access is temporarily suspended.", "reason": "<admin's note>" }
```

Parent app must render a dedicated screen showing the reason and a "Contact school" CTA — NOT a generic error toast. Only the Academics tab is blocked; Attendance / Behavior / Pickup QR / Dismissal History stay fully accessible (safety information must never be gated).

## Flutter conventions (both apps)

- **Router refresh on session change**: `GoRouter.redirect` does not re-run when a Riverpod provider changes. Both `router.dart` files bridge `sessionProvider` → `refreshListenable` via a `ValueNotifier<int>` incremented inside `ref.listen(sessionProvider, ...)`. Without this the splash redirect fires once at boot, sees `session.isLoading`, and never navigates away when `/me` resolves.
- **Theme text scaling must be null-safe**: Material 3's base `TextTheme` has entries with `fontSize == null` (geometry is applied later). Calling `.apply(fontSizeFactor: x)` on such a theme trips the `text_style.dart` assertion `fontSize != null || (fontSizeFactor == 1.0 && fontSizeDelta == 0.0)`. `vista_guard/lib/theme.dart` scales via a per-style helper that skips null-fontSize entries — don't replace it with `.apply()`.
- **Emulator base URL**: `env.dart` defaults `vistaApiBase` to `http://10.0.2.2:5000` (Android emulator loopback to host). Override via `--dart-define=VISTA_API_BASE=...` for physical devices.
- **Test stubs**: `test/widget_test.dart` in both apps is an intentional placeholder (`expect(1 + 1, 2)`), not the Flutter counter template. The real app entrypoints (`VistaParentApp`, `VistaGuardApp`) need a `ProviderScope` + routing context that a widget-test harness does not provide yet.
- **Postgres DECIMAL arrives as String**: node-postgres returns `DECIMAL`/`NUMERIC` columns as strings, not numbers. DTOs that blindly cast `json['x'] as num?` will blow up on any `sentiment_score`, `grade.score`, `risk_score`, etc. Use the `_toDouble` helper pattern (`num → toDouble`, `String → double.tryParse`, else null) seen in `models/grade.dart` and `models/behavior.dart`.
- **Android desugaring is required**: `flutter_local_notifications` needs Java 8+ APIs backported. `vista_parent/android/app/build.gradle.kts` sets `isCoreLibraryDesugaringEnabled = true` and pulls `com.android.tools:desugar_jdk_libs:2.1.4` — without these the debug build fails with `A failure occurred while executing com.android.build.gradle.internal.tasks.CheckAarMetadataWorkAction`.
- **Student IDs are UUIDs, not integers**: the `students.id` column is `UUID`. Any backend middleware that touches a student ID from `req.params`/`req.query` must treat it as a string — the previous `parentScope.js` parsed it with `Number.parseInt` and silently truncated `4186f23e-…` to `4186`, triggering `invalid input syntax for type uuid`. Validate with a UUID regex, never `parseInt`.
- **TabBar on navy AppBar needs explicit label colors**: Material 3 defaults `labelColor` to `colorScheme.primary` (navy), which is invisible against the navy AppBar. `ChildDetailScreen`'s TabBar sets `labelColor: Colors.white` + `unselectedLabelColor: Colors.white70` + `indicatorColor: Colors.white` explicitly — don't rely on theme defaults for any TabBar sitting inside a `VistaColors.brand` AppBar.
- **Risk tier strings are the full DB enum**: `/api/ai/parent-summary` returns `risk.tier` verbatim from `risk_assessments.risk_level`, which the DB constrains to `'Stable' | 'Moderate Risk' | 'High Risk'` (not `'Moderate'`/`'High'`). `widgets/risk_chip.dart` switch cases must match those exact strings, or the chip falls through to the gray "Unknown" default.
- **Parent risk-card driver thresholds**: `_RiskCard` / `_driversFor` in `vista_parent/lib/screens/child_detail_screen.dart` map `risk.factors` to plain-language sentences with these cutoffs — `attendance < 0.85`, `academic < 0.80`, `competency < 0.70` (ECE only), `behavioral < 0.0` (signed VADER, NOT 0–1 — see root CLAUDE.md correction). These mirror risk.py's "medium" cutoffs so the explanation always agrees with what nudged the tier above Stable. The drivers section is hidden entirely when `tier == 'Stable'` so we never manufacture concern; for ECE students the academic driver is replaced by the competency one. Severity sort is "lower = worse" — for behavioral that means using `1.0 + beh` so the signed VADER value sorts consistently against the 0–1 factors.
- **Deep-link tab navigation in `ChildDetailScreen`**: tabs (Overview / Attendance / Academics / Behavior / Pickup QR / Dismissal) are owned by the screen's `TabController`. To jump from one tab body to another, use the `_jumpToTab(String name)` callback the parent state passes down (e.g. `_OverviewTab(onJumpToTab: _jumpToTab)`) rather than reaching for `DefaultTabController.of(context)` — the screen uses an explicit `TabController`, not a `DefaultTabController`, so the inherited lookup returns null. Names come from the file-scope `_tabNames` list.
- **Pull-to-refresh needs `AlwaysScrollableScrollPhysics` on short/empty lists**: `RefreshIndicator` only fires when the child is scrollable. A `ListView` with one row or an empty-state message is not scrollable by default, so the pull gesture never triggers `onRefresh`. Every refreshable tab in `child_detail_screen.dart` (Overview, Attendance, Academics, Behavior) wraps its loading/empty/data branches in a ListView with `physics: AlwaysScrollableScrollPhysics()` — keep this when adding new tabs.
- **Guard `gateSettingProvider` (SharedPreferences)**: `vista_guard/lib/settings.dart` exposes a `StateNotifierProvider<GateSetting, String>` backed by SharedPreferences key `gate_label`, options locked to `['Gate 1', 'Gate 2']`. Read once with `ref.read(gateSettingProvider)` at submit time in `scan_result_screen.dart` so the value passed to `GuardApi.verify(gateLabel: ...)` and the offline-queue enqueue is the gate set when the scan happened, not the gate at sync time. The Settings screen (`/settings`, accessed via the gear icon in the Scan AppBar) is the only writer.
- **Guard offline queue is SQLite v3**: `vista_guard/lib/offline_queue.dart` opens `vista_guard_queue.db` at version 3; `onUpgrade` adds `gate_label TEXT` (v1→v2) and `fetcher_type TEXT` (v2→v3) to the existing `scan_queue` table. `enqueue` and `_drain` carry both fields through. Stale v1/v2 rows queued before this session still drain successfully because both columns are nullable end-to-end (the server defaults `fetcher_type` to `'self'` when absent on `/verify`).
- **Pickup QR fetcher binding**: the `_PickupQrTab` chip selector in `vista_parent/lib/screens/child_detail_screen.dart` calls `generateQr(studentId, fetcherType, fetcherId)` whenever the user picks a different chip — every selection actually issues a fresh server-side QR so the bound fetcher matches the visible QR. The chip-list "self" entry uses `sessionProvider.valueOrNull.photoUrl` for the avatar; "auth" entries come from `parentApi.listAuthorizedPersons(studentId)` reloaded after the manage screen pops.
- **Pickup QR "Download QR" → labeled poster PNG**: when the selected chip is an authorized person (not 'self'), `_QrCard` shows a "Download QR" outlined button. The button label is intentionally not "Upload" / "Send" — "Upload" reads as uploading *to* the app, "Send" suggests an in-app DM channel that doesn't exist; "Download" matches the save-to-device action. The exported PNG is **not** the bare QR — `_composePickupQrPng()` paints a 800×1180 poster with navy "VISTA Pickup QR" header band + timestamp, the QR centered on a white rounded card with a slate border, a labeled info block (`STUDENT` + name + grade·section, `AUTHORIZED FETCHER` + name with relationship), and a footer pill reading "Present this at the school gate. Auto-invalidates after one scan." Rendering is direct `Canvas` + `TextPainter` (no widget tree, no `RepaintBoundary`, no `BuildContext` dependency) — bytes go through `PictureRecorder.endRecording().toImage(...).toByteData(PNG)`, then `Gal.putImageBytes(bytes, album: 'VISTA', name: 'vista-pickup-<student>-<ts>')` writes them to the device gallery. The QR module itself uses the modern `eyeStyle` / `dataModuleStyle` API (the legacy `color` / `emptyColor` on `QrPainter` is deprecated) and is painted over a Canvas-drawn white rect so the saved PNG has solid contrast on dark themes. Permissions go through `Gal.hasAccess(toAlbum: true)` / `requestAccess(toAlbum: true)` — add-only scope, never the read-gallery scope. **iOS** needs `NSPhotoLibraryAddUsageDescription` in `ios/Runner/Info.plist`; **Android** needs `WRITE_EXTERNAL_STORAGE` with `android:maxSdkVersion="28"` plus `ACCESS_MEDIA_LOCATION` in `AndroidManifest.xml` (API 29+ uses MediaStore with no runtime grant). After save, a SnackBar confirms with the fetcher's name. The button is hidden on the 'self' chip — that QR is timed and the parent uses it at the gate themselves, so saving it as a photo doesn't fit the flow.
- **Guard scan result avatar**: `vista_guard/lib/screens/scan_result_screen.dart` renders `_FetcherAvatar` (`CircleAvatar` with `NetworkImage(guardian.photoUrl)`, initials fallback, small green check badge) instead of the prior generic check icon. The badge is a `Stack` with `clipBehavior: Clip.none` so it overflows the avatar — don't move it inside a clipped container or the badge disappears.
- **Image picker permissions (vista_parent)**: `image_picker: ^1.1.2` is wired up. iOS needs `NSCameraUsageDescription` + `NSPhotoLibraryUsageDescription` in `ios/Runner/Info.plist`; Android 1.x doesn't need extra permission strings. The shared bottom-sheet helper lives at `vista_parent/lib/widgets/photo_picker.dart` (`pickPhoto(context)` returns a `File?`) and is reused by both the authorized-pickup form and the Edit Profile avatar tile — don't duplicate the camera/gallery action sheet in new screens.
- **Guard typography uses `google_fonts` for DM Sans, not bundled TTFs**: `vista_guard/lib/theme.dart` resolves DM Sans via `GoogleFonts.dmSansTextTheme(base.textTheme)` (cached at runtime, no asset shipping). Don't add a `flutter: fonts:` block to `vista_guard/pubspec.yaml` — the previous attempt failed at `assembleDebug` because the TTFs weren't checked in. The AppBar `titleTextStyle` and `FilledButton` `textStyle` use `GoogleFonts.dmSans().fontFamily` so they pick up the same loaded font outside the TextTheme inheritance chain. First launch with no internet falls back to the platform default and DM Sans appears on the next launch with connectivity.
- **Guard scan reticle**: `vista_guard/lib/screens/scan_screen.dart` overlays a 260×260 framing reticle on the camera (`MobileScanner`) with four 36-px white corner brackets (16-px outer corner radius). The earlier kit-spec horizontal green scan line was removed at the user's request — don't reintroduce it. The scaffold background is `VistaColors.scanBg = #1A1F2A` (darker than the app's `#F5F7FB` surface) — set this when adding any screen that sits behind the camera, not the global theme. Source-of-truth: VISTA Guard UI kit `GScanScreen` in `C:\Users\Jerome\Downloads\_vista_guard_kit_scripts\script_3_*.jsx`.
- **Login screens share a polish pattern across both apps**: `vista_guard/lib/screens/login_screen.dart` and `vista_parent/lib/screens/login_screen.dart` both render a Row(64×64 `ClipOval` logo with a navy `BoxShadow` halo + Column(title w800 + subtitle)), followed by a white form card (rounded 20, hairline `#E3E7EF` border, soft navy shadow), with `prefixIcon`s on email/password, an eye toggle that flips `_obscure`, and a duplicated `_ErrorBanner` widget (tinted danger bg + icon, NOT bare red text). Both override `Scaffold.backgroundColor` to `#EEF1F7` — explicitly lighter than the global theme's `#F5F7FB` so the white card lifts. The guard variant additionally pins an "Authorized personnel only" footer to the viewport bottom via `LayoutBuilder` + `IntrinsicHeight` + `Spacer` (NOT `Scaffold.bottomNavigationBar`) so the footer sits at the bottom only when the form is short — keep that wrapper pattern if you add a footer to the parent variant. The parent app's earlier centered-NRYS / 120-px logo design was replaced with the row layout to match guard; don't reintroduce the centered block.
- **Guard sign-in forces a gate pick before the camera**: `gateConfirmedProvider` (per-session `StateProvider<bool>`, defaults `false`) gates the `/scan` route — the router redirects any logged-in guard whose flag is still `false` to `/gate` (`screens/gate_select_screen.dart`), and only flips to `true` when the guard taps Continue on that screen (which also persists the choice via `gateSettingProvider.set`). Sign-out resets the flag so the next login re-prompts. The provider is intentionally NOT persisted: cold-launching with a stored session must still force a re-pick because a new shift may inherit the device with yesterday's gate persisted in SharedPreferences. The mid-shift switcher in Settings is unchanged — that path writes `gateSettingProvider` only and does not touch the confirmed flag.
- **Guard Settings is the sign-out surface**: `vista_guard/lib/screens/settings_screen.dart` (route `/settings`, gear icon in the Scan AppBar) holds both the Gate radio group and an Account section with a destructive Sign out button. Sign out calls `authRepositoryProvider.logout()`, resets `lockedProvider` so the next sign-in doesn't immediately face the PIN gate, then `ref.invalidate(sessionProvider)` — the router's `refreshListenable` picks up the session change and redirects to `/login` automatically. There is intentionally no sign-out icon on the Scan AppBar (it already has Today's Log + Settings + Lock); keep all account actions on the Settings page.
- **Guard Forgot PIN is gated on the server password**: `vista_guard/lib/screens/pin_lock.dart` is a `ConsumerStatefulWidget` (it needs `ref` for the reset flow). When a PIN is already set, a "Forgot PIN?" `TextButton` appears under Unlock; tapping it prompts for the signed-in account's password, calls `authRepositoryProvider.login(email, password)` to verify (which also rotates tokens — fine, it's the same role-checked endpoint as initial login), then deletes the `vista.guard.pin` secure-storage key and flips `_settingUp = true` so the same screen now collects a new PIN. **Don't replace this with a local-only reset (e.g. a "skip" button or a hidden gesture)** — local clearance is security-equivalent to no PIN at all for someone holding an unlocked phone. The PIN's whole purpose is the threat model where the device is taken; gating reset behind the server password preserves that. The link is hidden during initial setup (no PIN to forget yet).
